# Plugin Hub reviewer map

**From Scratch**, author **Pilots r kwl**, is a voluntary fresh-start item-progression challenge on an existing OSRS character. Players keep their levels, achievements and real bank; the plugin tracks earned challenge ownership separately. It does not block withdrawals, enforce Ironman rules or automate gameplay. Each character's progression is local; friends play separate challenges without synchronization or a leaderboard.

Production entry point: `com.fromscratch.FromScratchPlugin`. Package `com.fromscratch`, config group `fromscratch`, official internal/storage name `from-scratch` (published beta: `from_scratch`), `build=standard`, Java 11, BSD-2-Clause. Existing beta releases remain separate from official Hub submission. Submission/review is not approval or verified listing availability.

## Official audit sources

Checked on 2026-10-28: [submission instructions](https://github.com/runelite/plugin-hub#submitting-a-plugin), [review scope](https://github.com/runelite/runelite/wiki/Plugin-Hub-Review), [rejected features](https://github.com/runelite/runelite/wiki/Rejected-or-Rolled-Back-Features), [Jagex guidelines](https://secure.runescape.com/m=news/third-party-client-guidelines?oldschool=1), and [example plugin](https://github.com/runelite/example-plugin).

The audit found and removed a direct BankTagsConfig setter because the current rejected-feature list excludes modifying another plugin's configuration. From Scratch now delegates selection and stale-owned-selection cleanup to the documented [BankTagsService API](https://github.com/runelite/runelite/blob/master/runelite-client/src/main/java/net/runelite/client/plugins/banktags/BankTagsService.java). Bank Tags owns its resulting remembered-tab persistence. This distinction is our audit assessment, not an upstream policy approval. No other explicit published-rule conflict was identified; the integrations below remain intentionally disclosed for human review.

## Data, storage and network

- [RuneLiteBankSource](../src/main/java/com/fromscratch/bank/RuneLiteBankSource.java) reads the complete BANK API container, identity/profile metadata for local isolation and supported on-demand contents evidence. Search, visible widgets and native tabs never define physical ownership. No ongoing inventory/equipment ownership tracking.
- [BankRepository](../src/main/java/com/fromscratch/persistence/BankRepository.java), [BankRunCodec](../src/main/java/com/fromscratch/persistence/BankRunCodec.java) and [ProgressBackup](../src/main/java/com/fromscratch/persistence/ProgressBackup.java) use plugin-scoped Filepath streams/channels on the storage worker. Journals/checkpoints are forced before atomic current replacement; revision/CAS and lifecycle guards reject stale work. Failure preserves evidence, not a new run. Saves contain local character/run identity and activity evidence, are private and unencrypted, and never synchronize to a server.
- Exports/imports use the explicit Filepath chooser, bounded checksummed same-character archives, preview/confirmation, preserved prior progression and atomic replacement; histories are not merged. Reset requires confirmation and an acknowledged recovery archive. Formats 5 through 11 and original migration evidence remain supported as documented in [accounting](technical/ACCOUNTING.md).
- [PriceService](../src/main/java/com/fromscratch/wealth/PriceService.java) calls injected RuneLite ItemClient bulk public guide prices on a separate price worker. From Scratch sends no holdings, character identity or credentials. No custom backend, telemetry or cloud service. Fixed buyback prices never use live rates. Normal RuneLite authentication/game/update traffic remains RuneLite's responsibility.
- Host Time Played uses logged-in ticks, not mobile or wall-clock run age. GE history derives finalized observed lifecycles without claiming unseen collection destinations or verified tax where estimated.

## Identifier and offline migration gate

The official Hub marker is `plugins/from-scratch`; `PluginDescriptor.internalName` is `from-scratch` and RuneLite supplies its normal scoped `.runelite/plugin-data/from-scratch/` directory. Published beta versions used `.runelite/plugin-data/from_scratch/`. The [packager rules](https://github.com/runelite/plugin-hub-tooling/blob/v5/package/src/main/java/net/runelite/pluginhub/packager/Plugin.java) reject underscores and require the compiled descriptor to match the marker.

The implemented [offline migration utility](../src/migration/java/com/fromscratch/migration/OfflineProgressMigration.java) is a separately executed Java 11 owner tool, excluded with its tests from the official standard build. It requires all RuneLite and From Scratch clients closed and explicit typed authorization. It copies the complete legacy tree without rewriting save schemas, changing original file bytes or deleting the original directory. Conflicting destination files, symbolic links, junctions/reparse points and unsupported objects are refused. Independent copies are SHA-256 verified; resumable staging retains transaction evidence, and a no-clobber completion receipt is published last. Empty operational lock files are held where present and omitted from the copy; copying lock bytes would not transfer a lock. See [maintainer commands and filesystem limitations](MAINTAINING.md#offline-progression-migration).

Preserved progression layout:

| Relative location | Evidence preserved by the offline copy |
|---|---|
| `characters/<unchanged-character-key>/` | `current.json`, `previous.json`, pending saves, bank journals/checkpoints, item-ledger files, historical migration/reset archives and their manifests. Bank state includes legacy snapshots, signed balances, GP, buyback receipts/entitlements, GE and Potion Storage evidence. |
| Same character directory, `restored-directory.json` and `restored-<UUID>/` | Import selection pointer, selected progression, retained prior trees and damaged/recovery evidence. The whole tree is copied, not only the selected checkpoint. |
| Same character directory, `playtime/`, and selected restored tree's `playtime/` | Run-specific playtime checkpoints, backups and pending records. Peak checkpoints/backups belong to the corresponding economic tree. |
| Root-level `progress-import-*` staging | Interrupted import evidence is retained. |
| Explicitly chosen external `.fsp` exports | Remain at their user-selected locations, outside the plugin's scoped tree. |

Production uses only the canonical scoped Filepath root; it does not inspect or copy the beta sibling and does not broaden filesystem access through `Filepath.Unchecked`. [PluginDirectoryCapabilityTest](../src/test/java/com/fromscratch/persistence/PluginDirectoryCapabilityTest.java) retains evidence of the scoped API boundary that makes an external offline transfer necessary.

[CanonicalStorageGate](../src/main/java/com/fromscratch/persistence/CanonicalStorageGate.java) is shared by economic storage and playtime before progression IO. It validates the canonical `.from-scratch-migration-complete` receipt format and repository cutover evidence. The receipt records the original transaction's manifest digest; it is not a continually recomputed hash of legitimate later progression. Missing, malformed or conflicting evidence alongside existing canonical data blocks storage instead of creating a new challenge. Genuinely new installations require explicit new-installation confirmation, available only for an empty canonical directory, followed by normal bank setup. The plugin cannot distinguish an empty new installation from unmigrated beta data outside its scope, so existing beta players must follow the migration guidance rather than select new installation.

The owner reports successful migration of existing progression and completion of manual acceptance testing before authorizing submission. Existing migrated progression is preserved by the cutover. This owner report is separate from automated fixtures and does not imply testing on every filesystem or client scale. After cutover, canonical progression is authoritative: completed migration does not reimport stale beta data. Original beta and new plugin histories do not synchronize or merge; do not continue the same challenge in the obsolete beta.

Hub metadata now omits `version`: the standard packager falls back to the source commit. Gradle and native beta toolchain versions remain independent and unchanged. Discovery tags use separate `fresh,start` entries in both definitions.

## Native bank and UI integration

| Integration | Source and actual behavior | Review-sensitive boundary |
|---|---|---|
| Virtual Bank | [VirtualBankMode](../src/main/java/com/fromscratch/bank/VirtualBankMode.java) registers immutable membership with public TagManager runtime methods and opens/closes through BankTagsService using NO_LAYOUT/HIDE_TAG_NAME. | The active core plugin's Guice injector supplies companion services. Read-only Bank Tags settings/tag-layout keys distinguish owned temporary UUID tags from saved user tags. No direct config setter, user tag/layout deletion or ALLOW_MODIFICATIONS flag. Public service calls have core-managed remembered-selection side effects. Foreign active/saved tags are preserved. |
| Native tabs/search | The same class and [plugin event handlers](../src/main/java/com/fromscratch/FromScratchPlugin.java) use bankBuildTab/bankSearchFilter, native current-tab counts and search mode/query state. Membership vetoes only items outside earned ownership after native matching. | Callback stack shapes and native bank scripts are implementation-coupled. Whole-bank search layout is retained: forced single-tab layout would enter the native meslayer_close branch. Deferred reconciliation preserves input, preferences and Potion Storage transitions. No query/input write, injected key/click, menu action or tag-reopen loop. |
| Quantity display | [VirtualBankOverlay](../src/main/java/com/fromscratch/overlay/VirtualBankOverlay.java) temporarily sets each eligible native item's public quantity-display mode to NEVER, then [BankItemPainter](../src/main/java/com/fromscratch/overlay/BankItemPainter.java) redraws the actual physical count in gray after tinting and draws signed virtual counts. | This is a scoped native widget display-flag mutation, not an entirely draw-only implementation. Original modes restore when inactive/closed/reset/disabled; dragging retains native counters. IDs, quantities, sprites, slot positions, clipping, hitboxes and menus are unchanged. Other plugins affecting the same display modes may require compatibility review. |
| Title | VirtualBankMode changes native bank title text while its view is selected and restores prior text where safe. | Presentation-only in-game widget text. No core RuneLite root-frame/sidebar manipulation, overlay/infobox relocation or anchor modification. |
| Potion Storage | [RuneLitePotionSource](../src/main/java/com/fromscratch/potion/RuneLitePotionSource.java) reads enums/varbits and queries POTIONSTORE_DOSES, also used by [core Bank Tags' PotionStorage helper](https://github.com/runelite/runelite/blob/master/runelite-client/src/main/java/net/runelite/client/plugins/banktags/tabs/PotionStorage.java). It immediately reads integer stack slot 0 for each potion enum. [PotionStorageOverlay](../src/main/java/com/fromscratch/overlay/PotionStorageOverlay.java) draws cached signed units after the native interface with bounds/font clipping. | This executes cached client script code and changes shared interpreter stack state; it is not claimed entirely side-effect-free. The client-thread API is non-reentrant: observations run outside script callbacks, which only invalidate freshness. RuneLite restricts packet-sending scripts by default; From Scratch never enables packet permission or calls deposit/withdraw scripts. Native row/script structure remains implementation-coupled. Incomplete stock is unknown, never zero. |
| Examine/notifications | [NativeExamine](../src/main/java/com/fromscratch/examine/NativeExamine.java) observes the existing Examine action/response and queues one bounded local supplemental message after native/core price handling. | Sidebar/overlays | [BankSidebar](../src/main/java/com/fromscratch/bank/BankSidebar.java) and [BankOverlayRegistration](../src/main/java/com/fromscratch/overlay/BankOverlayRegistration.java) register/remove the plugin's own ClientToolbar navigation and overlays. | Uses normal extension registration; does not rearrange or mutate other plugins' Swing components, overlays, anchors or configuration. |

Quantity modes are prepared before native rendering, not by changing physical stack amounts. Rebuilt/replaced, hidden and dragging widgets restore their captured mode; inactive bank/settings restore all retained modes on the next preparation. Plugin shutdown schedules `clearCache` on the client thread. Restoration only replaces a mode still set to NEVER, so a later different mode from another plugin is not overwritten. Native tab/search transitions reuse this same lifecycle. Automated overlay fixtures cover presentation and cleanup; owner checks must still exercise native rendering and interaction at their UI scale.

## Accounting and user confirmations

[BankController](../src/main/java/com/fromscratch/bank/BankController.java) coordinates client-thread observations, EDT UI and serialized worker commits. Rendering uses cached acknowledged projections. Startup/shutdown do not block; scheduled price work is canceled and executors stop without synchronous waiting.

[BuybackCatalog](../src/main/java/com/fromscratch/buyback/BuybackCatalog.java) and its existing engine/state/receipt model enforce fixed prices, qualifying legacy items, finite shared/exact-copy entitlements, UUID payment identity and no GP overdrafts. Payment, entitlement, contents offsets where supported and audit evidence commit atomically; failed persistence grants/spends nothing. Old prices and receipt meaning remain intact. Complete outfits require all pieces; approved transformations cannot multiply copies; quiver upgrades total 60M rather than 75M. See [fixed prices and variants](technical/BUYBACK_PRICING.md).

Pouch/bag native contents proofs remain separate from ownership. Unknown contents are never empty. Gathering containers/quiver ammo require two unchecked empty/shared-store and already-accounted declarations, scoped to revision/time; positive native evidence can veto them. Receipt provenance distinguishes player declarations from native proof. Manual corrections, import and reset remain explicit local confirmations, never inferred game actions.

## Production artifact and forbidden-behavior audit

- [Metadata](../runelite-plugin.properties) selects only `com.fromscratch.FromScratchPlugin` with standard build. Root icon is a genuine 48x48 PNG; navigation resource is 24x24 and loaded from the JAR. [License](../LICENSE), [NOTICE](../NOTICE) and [artwork provenance](ARTWORK.md) retain attribution.
- The official standard template compiles `src/main` independently of custom beta launchers. No third-party runtime dependencies beyond RuneLite's supplied API/client libraries were added; Lombok is compile-time only. No Plugin service-provider registration. Beta/preview/test classes and the standalone migration utility/tests do not enter the production artifact.
- Production audit found no synthetic gameplay input, menu-action/packet APIs, credential handling, custom HTTP service/client, reflection, JNI/JNA/Unsafe, dynamic downloaded code/classloading, external process execution or Java object serialization. Streams/channels come through Filepath; client/Swing/storage/price threads remain separated. Diagnostics are DEBUG, local and bounded.
- `src/beta`, `src/preview`, `src/migration`, `src/migrationTest`, `beta/windows*` and their scripts are separate owner tools with active consumers. The beta packages unmodified upstream dependencies and a private runtime, retaining notices. Their process/filesystem/installer code is excluded from the standard plugin JAR. Published installer execution validation remains separately deferred under local Windows Application Control.

## Validation and review status

Use [the validation plan](technical/TEST_PLAN.md) and [maintainer commands](MAINTAINING.md). Focused lifecycle/resource/historical-save tests, production-only official standard build, local Markdown/PNG checks and exact-commit Windows/Ubuntu CI support the submission. They do not establish RuneLite approval, native focus on every scale, or beta installer execution success.
