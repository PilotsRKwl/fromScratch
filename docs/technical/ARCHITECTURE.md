# Architecture

Production architecture for From Scratch. The [reviewer map](../PLUGIN_HUB_REVIEW.md) describes supported APIs, review-sensitive integration and validation boundaries. Git history retains superseded designs.

## Core and observation

`com.fromscratch.FromScratchPlugin` owns registration and shutdown. `bank/BankController`, `RuneLiteBankSource`, `BankSidebar` and `persistence/BankRepository` are the production path. Test-only historical controllers are not production dependencies.

The full `InventoryID.BANK` API container is the ongoing quantity authority. A mounted normal bank, no PIN and a complete observation at the next GameTick boundary establish readiness. A non-null empty array is valid; unavailable/partial data is unknown. Cached observations invalidate on relevant lifecycle/container changes. Visible widgets, tab contents and search results never define physical quantities.

Initial setup uses the player's inventory/equipment banking attestation and explicit confirmation. It captures the full physical container before an acknowledged initial save can activate Virtual Bank. No ongoing inventory/equipment ownership tracking or gameplay enforcement is introduced.

`potion/RuneLitePotionSource` separately observes Mixology storage. Supported enums define dose/item identities; the same read-only dose script used by core Bank Tags reads total units. Native build/dose-change events establish freshness; quantity varp triggers invalidate the cache. No unopened/unreadable container is assumed empty. The unlocked flag can establish that a character has no store. All reads are client-thread-only and outside rendering.

`PotionState` belongs to `BankRun`, and `PotionUpdate` belongs to its durable audit. `PotionEngine` reconciles copied bank/storage snapshots in one commit, with once-consumed same-bank-session withdrawal budgets for delayed returns/conversions. The observation session is separate from budget/session identity, so processing bank changes cannot make stale storage current. Existing-run unknown stock or ambiguous sources require an explicit recorded review. Original bank and storage baselines remain immutable after verification.

## Views and information

- `bank/VirtualBankMode` uses supported Bank Tags APIs and immutable eligible-ID snapshots. Native bank tab slot ranges intersect with positive virtual membership. Membership callbacks do set lookups, with no item-definition, disk, price or ledger work. Re-entrant close paths clear state first. Filtering requires the correct active run, identity, ready bank and saved preference; before setup and after reset the full bank remains available. Native search keeps the cached ownership intersection; another independent Bank Tag can leave the view safely. No repeated activation loop.
- `overlay/VirtualBankOverlay` and `overlay/BankItemPainter` preserves native interactions and geometry. M9.2 temporarily changes the public quantity-display mode, draws the physical counter in gray after the locked tint, and restores original modes when inactive. It does not change item IDs, sprites or quantities. Virtual counters retain configurable color and compact formatting. See the reviewer guide for the precise rendering disclosure.
- Native item Examine correlation waits for the game's normal response and RuneLite price handling before one local supplemental line. Exact signed quantities and numerical color segments are bounded to avoid native chat truncation. Prices are cached; no separate menu action or outgoing player chat is created.
- History windows query retained evidence asynchronously, with bounded pages. Item history is read-only. No expanded statistics page or fake bank inventory exists.
- `bank/Overdrafts` derives warnings only from newly acknowledged automatic physical changes in a continuous observed bank session. `FromScratchPlugin` queues local red chat and supported RuneLite notifications; sidebar debt is derived from saved signed balances, independent of Virtual Bank. Initial/import/manual/correction/replayed states do not generate alerts. `OutstandingPanel` uses the existing EDT projection and item-history navigation. There is no active-run Potion Storage sidebar list.
- `bank/BankSetup` keeps the inventory/equipment attestation, pending full-bank proof and optional unknown-unlock answer on the client thread, scoped to character and setup attempt. `bank/PotionSetupPanel` and runtime-only `potion/PotionCapture` expose the exact complete native capture. A native build must precede dose changes; all enum quantities, including zero/nonvisible types, are read and checked against native row units/amounts. Character changes, dirty/unavailable data and reset invalidate proof. Supported unlock evidence skips the storage step for a verified locked character; only an unknown state needs explicit not-unlocked attestation. A verified pending bank remains usable from Potion Storage if its complete API quantities/session still match. Changed bank quantities invalidate a storage-mode pending capture until the full bank is recorded again. Full bank and storage baselines commit together; no persisted observation can manufacture setup proof.
- `overlay/PotionStorageOverlay` draws after the complete native bank interface, using its five-child rows and public native font metrics. It clips through parent bounds and preserves physical text, geometry, widgets and interactions. Cached projection labels follow configured color; debt/unverified labels use warning color. Insufficient inline space falls back to a compact FS marker with an exact tooltip. `BankOverlayRegistration` registers/removes both overlays once.
- `BankCorrectionDialog` exposes Bank Items / Potion Storage. Storage corrections use `STORAGE_REVIEW` evidence in the existing atomic checkpoint, revision/identity guards and checked signed arithmetic. Last verified physical data is labeled cached; it never becomes a new observation session. Changed types invalidate their transfer budgets, preserving unrelated types. Before/after adjustments derive from retained predecessor checkpoints for paged history. No schema change is needed for this UI update.
- The native Potion Storage button pauses From Scratch's item-tab filtering before core Bank Tags handles the same navigation. Cleanup stays deferred and state clears first. Returning to a normal item tab resumes the cached native-tab intersection without reopening a tag or changing the saved preference. Closing storage/the bank clears the pause. This narrow special-view guard does not filter or rebuild the potion interface itself.

## Bank Tags configuration ownership

From Scratch registers a runtime predicate and uses the documented BankTagsService open/close API. Bank Tags manages its own remembered selection as part of those service operations. From Scratch reads that state to recognize its temporary UUID tags, but never writes BankTagsConfig or another plugin's configuration directly. An owned inactive stale selection is closed through the public service without resetting search input; a foreign active or saved tag is preserved. Core may remember the temporary view while active, and normal close/stale cleanup clears it through the service. No user tab or layout is deleted. The lifecycle tests cover stale startup, explicit OFF, foreign selections, re-entry, search, native tabs and Potion Storage.

## Accounting services

See [ACCOUNTING.md](ACCOUNTING.md) for the signed equation, GP spending, valuations and finalized GE view. `BankEngine` applies checked arithmetic to immutable runs. GE observations preserve cumulative fill evidence and durable slot generations; presentation aggregation does not replay financial effects.

`buyback/BuybackCatalog` and `BuybackEngine` own approved prices, copy roles, variants and eligibility. Rune Pouch and Looting Bag purchases atomically commit one family entitlement, fixed GP payment and verified negative legacy-content adjustments. When native Looting Bag evidence is unavailable, the existing purchase confirmation offers a voluntary empty-bag declaration. `BankController.buyBag` revalidates character/run revision, full bank, one supported bag, definitions, funds and entitlement, rejecting any current verified nonempty evidence. `BuybackPurchase` distinguishes `PLAYER_CONFIRMED_EMPTY` from native empty/nonempty proofs; it carries zero contents adjustments. No separate ledger or contents wizard is introduced. Narrow contents readers remain on-demand proofs, not an ongoing personal-container quantity authority.

`wealth/PriceService` obtains RuneLite bulk guide prices on a separate worker. It never sends holdings or character identity. Current signed valuation, confirmed expenditures and run-scoped peak measurement stay distinct. `playtime/PlaytimeTracker` counts logged-in host ticks and checkpoints efficiently; it does not use elapsed run age or claim mobile playtime.

## Persistence and threads

All progression IO uses Filepath on the background worker. A forced journal/checkpoint precedes atomic current replacement; acknowledged commits alone become UI/rendering authority. Revision/CAS checks reject stale work, and callbacks are guarded by identity/run/lifecycle. Existing saves, immutable baselines and exact migration/recovery evidence are preserved. A load failure is not permission to create a new run. Reset archives before acknowledgment.

Milestone 10.7 extends the economic checkpoint to format 10 for dose state and audit evidence. Format 9 loads without rewriting; the next acknowledged transaction writes format 10 through the existing journal/checkpoint/atomic path. Formats 1 through 8 retain their previous verified migration paths. Format-9 `.fsp` exports remain readable. Playtime and peak keep their small separate checked records. Import verifies a bounded checksummed archive and matching character, previews replacement, preserves the prior run and atomically selects the restored tree. Histories are never silently merged.

Client APIs run on the client thread, Swing work on the EDT, disk/price work off both. Startup/shutdown do not wait synchronously between these threads. Listeners, overlays and optional view state are cleaned up on shutdown.

## Distribution boundaries

The production `src/main` plugin uses no custom backend, cloud sync, credential access, reflection, native process execution, synthetic gameplay input or withdrawal blocking. RuneLite handles its normal authentication and game connection.

`src/preview` renders the same production Swing components with explicit synthetic data and official sprites; it never launches the game or loads player progression. The offline migration utility has its own source set and tests. Neither utility enters the production JAR or standard Hub build.

## Exact-copy buybacks

The existing buyback transaction, GP commitments and projection are extended, not replaced. Historical role levels still grant one shared copy (including pouch/bag and Void tiers). New catalog entries explicitly use exact-ID roles `copy_<item ID>` whose integer entitlement is the receipt-derived count, not an upgrade level. Their encoded level is always 1 and quantity is the paid copy count. Each receipt has a dedicated `selected: {item, quantity: 1}` object; pouch/bag evidence is never reused. Constructors validate the allowlisted catalog/ID, one-copy quantity, complete floor keys, total GP, duplicate UUIDs and receipt-derived counts. The existing ledger is bounded at 4,096 purchases; reaching that limit rejects a purchase without spending.

One exact copy costs 1M for Slayer gear or 30K for each Elite Black Knight piece. Only the eleven explicit ordinary Black Mask charge IDs bypass the tradeability exclusion; notes/placeholders and arbitrary tradeables remain rejected. The reviewed 104 Slayer IDs include 44 mask IDs and 60 helmet IDs. Native item definitions remain required at confirmation.

Per-ID bank floors follow the existing signed return-protection rule. At first payment floor = min(0, raw balance); repeated payments add one paid copy without moving the floor. Returns may raise the floor to zero, never lower it. Available physical copies are the natural signed bank progression plus the paid allowance, capped by physical stock. No new gain, physical mutation or raw bank credit is fabricated. A withdrawn paid copy must return before another payment for that same ID; this prevents reanchoring debt or refilling an out-of-bank copy. Other IDs never receive that allowance. Observed transformations use normal exact-ID bank deltas, without inferring inventory conversions or moving an entitlement across variants.

BankRun format 11 adds this evidence. Formats 5 through 10 remain readable; loading 10.7 format-10 bytes does not rewrite them. The next acknowledged transaction writes 11 while retaining journals and previous checkpoints. Historical receipt JSON stays unchanged. Older formats cannot contain selected-copy evidence. Backups/imports retain the same checksums, CAS, character/run isolation and atomic replacement. An older client must not load a format-11 save.

## Catalog families and empty stores

The catalog adds fixed-cost families and outfits without changing the existing catalog version or historical prices. Utility & Storage, Weapons, Armour and Skilling Outfits share a deterministic case-insensitive name/ID ordering in the catalog, tiles, dropdown and search. New equivalent families pool their signed bank deltas before purchase; a cosmetic, open/closed or imbued/unimbued transformation cannot manufacture an unpaid copy. Existing exact-ID Slayer purchases retain their original semantics. Quiver tiers share one role: 15M regular, 60M blessed directly, or 45M after the regular payment.

`EmptyStorageConfirmation` is an explicit player declaration for the five new gathering containers and regular/blessed quiver ammunition. Both unchecked declarations are required: the entire shared store is empty, and legacy contents are already in the initial baseline or have been corrected through Manual Bank Corrections. `StorageContentsGuard` reads only on purchase and vetoes nonempty current-session seed/tackle/quiver packets or available plank varbits. It never treats zero, missing or stale data as proof of emptiness and never tracks inventory ownership. The receipt's optional `storage` object records player provenance, with zero invented contents/offsets. Existing format-11 records and historical receipt encodings are unchanged; older formats reject the new declaration evidence. The existing atomic worker transaction still commits payment, entitlement and audit together.

During native search, `VirtualBankMode` preserves the whole-bank layout instead of forcing the single-tab branch that invokes `meslayer_close`. It reads public native search mode/query state and retains the ownership veto after native matching. No input is injected or reopened. The [validation plan](TEST_PLAN.md) separates automated lifecycle evidence from owner-only native UI verification. In the pinned RuneLite 1.13.4 BankMainBuild script, forcing bankBuildTab=1 jumps into single-tab mode; when bankmain_searching is true, that branch invokes meslayer_close. Preserving the native search layout prevents that input-closing side effect.
